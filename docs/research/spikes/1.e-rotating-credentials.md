# Spike 1.e: File-rotated database credentials with SqlClient pool clearing

## Question

Can an `IDbConnectionInterceptor` read credentials from a cached, file-backed `ICredentialSource` on `ConnectionOpeningAsync`, keep SqlClient pooling enabled, switch new connections to a rotated credential, clear the pool of the old credential after a grace period, and leave the old login with no sessions, without failing requests?

## Risk reduced

- Requirement `REQ-DATA-005`, database connections rotate credentials without disabling pooling (delivered by WP1.0, WP1.8, WP3.3, and WP3.4).
- Plan sections 8.4 and 8.8, which describe the interceptor, `RotatingCredentialSource`, and the Vault Agent file flow that Phase 3 builds on.
- [ADR-0008](../../adr/0008-secrets-broker-vault-over-openbao.md), which depends on rotation and revocation working inside the running app. This spike tests only the application side, as a local simulation. Vault is not involved.

## Time box and method

- **Time box:** one day or less. The spike took well under that.
- **Environment:** Windows x86-64, Docker Desktop, .NET SDK 10.0.401, and the digest-pinned SQL Server 2022 image from [spike 1.d](1.d-testcontainers-mssql.md) (server 16.0.4295.3).
- **Packages (checked 2026-10-06):** `Microsoft.Data.SqlClient` 7.1.1, `Microsoft.EntityFrameworkCore.SqlServer` 10.0.12, `Testcontainers.MsSql` 4.15.0, `xunit.v3` 4.0.1.
- **Method:**
  1. Each test creates a database and two SQL logins, `A` and `B`, both `db_owner` in that database, standing in for two Vault dynamic credentials.
  2. A `sql.json` file holds the current login. A file watcher (`FileSystemWatcher`) caches it in a `FileCredentialSource`, which raises an event with the old and new credential when the file changes. Rotation writes a temporary file and renames it over `sql.json`, which is how an agent that renders secrets to a file typically replaces it.
  3. A `DbConnectionInterceptor` overrides `ConnectionOpening` and `ConnectionOpeningAsync` and sets the connection string, with the current credential, before the connection opens. Pooling is on with a maximum of 30 connections.
  4. After a grace period, a janitor builds a connection with the old credential's connection string and calls `SqlConnection.ClearPool` on it.
  5. A revoke helper kills the login's sessions, drops the user, and drops the login, which is what a Vault revocation statement for SQL Server does.
  6. The test inspects `sys.dm_exec_sessions` to count sessions per login.

The pass criteria were fixed before the run:

| Criterion | Result |
| --- | --- |
| Pooling stays enabled, so sessions are reused | Pass |
| New connections use the new login after rotation | Pass |
| In-flight work on the old login completes | Pass |
| After the grace period the old pool is cleared and the old login has zero sessions | Pass |
| Revoking the old login afterward breaks nothing | Pass |
| The exact pool-keying behavior is documented | Pass |

## Results

Five tests ran twice in a row, and all passed both times (about 27 seconds per run).

- **Pooling stays on.** 200 operations at 8-way parallelism used 8 distinct database sessions before rotation and 8 after it. Every operation ran as the expected login.
- **Detection.** The file watcher saw the rotated file 4 to 5 ms after the rename.
- **Two pools while rotating.** Right after rotation the old login still held 8 idle sessions and the new login held 8. SqlClient keys a pool by the full connection string including the credential, so the old and new credentials have separate pools. Rotation therefore does not disturb the old pool, and it does not remove it either.
- **Clearing.** With a 2000 ms grace period, the old login's session count reached zero 2.02 to 2.04 seconds after rotation, which is the grace period plus a few milliseconds. Calling `SqlConnection.ClearPool` on a throwaway connection built from the old credential's connection string cleared the right pool.
- **Control without clearing.** With no janitor, the old login still held 8 sessions 6 seconds after rotation. Idle pooled connections do not go away on their own in that time. Dropping that login then failed with SQL Server error 15434, "Could not drop login ... as the user is currently logged in," so an uncleared pool also blocks revocation.
- **In-flight work survives clearing.** A 4-second query started on the old login before rotation finished on the old login while the pool was cleared mid-query (grace 1000 ms). The old sessions were gone 2 ms after the query returned. SqlClient marks in-use connections for closing and closes them when they return to the pool.
- **Revocation does interrupt in-flight work.** Killing the old login's sessions and dropping the login while a 5-second query was running made the query fail with a `SqlException`, error number 596, "Cannot continue the execution because the session is in the kill state." After that, new operations on the new login all succeeded.
- **Full lifecycle under load.** Six workers ran continuously through rotation, the grace-period pool clear, revocation, and two more seconds. In the runs made, the test completed between about 5,100 and 5,300 operations with zero failures. The old login served about 900 of them and the new login the rest.

### What the spike did not test

- **Vault itself.** No Vault Agent, no lease renewal, and no `rotate-root`. Phase 3 (WP3.3 and WP3.4) covers those.
- **Linux file events.** The watcher ran on Windows. The in-cluster file would be a memory-backed volume written by the agent, watched through inotify, and WP1.8's `RotatingCredentialSource` should add a periodic re-read as a fallback. Neither was tested here.
- **`SqlCredential`.** The spike builds the connection string with the user name and password. SqlClient's `SqlCredential` alternative was not compared.
- **EF Core context pooling.** The spike did not use `AddDbContextPool`.

### Findings to apply in later work

1. **The mechanism works as planned.** Overriding both `ConnectionOpening` and `ConnectionOpeningAsync` is enough. EF Core 10.0.12 opens the connection through the interceptor on every use, and setting `ConnectionString` on the still-closed connection is accepted.
2. **Use one function to build connection strings.** The pool key is the full string, so the interceptor and the janitor must build the old string identically, or `ClearPool` will clear nothing. The spike shares one helper.
3. **The grace period protects less than the plan implies.** Pool clearing never interrupts a running command. The real safety rule is about revocation: do not revoke the old credential until work that started on it has finished. With Vault, the old credential's lease keeps it valid after the new one is issued, so revocation normally happens well after the switch. WP1.8 should state this ordering (rotate, switch, clear, then revoke) next to the grace period, and keep the grace period as a bound on how long old idle sessions linger.
4. **Revocation needs the sessions gone first.** SQL Server refuses to drop a login that has live sessions (error 15434, seen in the control test), so revocation must either kill the sessions, as the spike's revoke helper does and as a Vault revocation statement for SQL Server is expected to, or wait until the pool is cleared. WP3.3 should confirm what the Vault MSSQL role's revocation statements do.
5. **Assert on SQL Server, not on the client.** Counting sessions in `sys.dm_exec_sessions` is a reliable proof that a pool was cleared and a login has no sessions. The `REQ-DATA-005` integration test should use it.

## Conclusion

**Answer:** yes.

An EF Core 10 interceptor over a file-backed credential source keeps pooling on, switches new connections within milliseconds of rotation, and a delayed `ClearPool` on the old credential's connection string leaves the old login with no sessions. In-flight work is safe across pool clearing and across the rotation itself. It is interrupted only by revocation, which the sequence avoids. Rotation, clearing, and revocation under continuous load produced no failures. WP1.8 can implement `ICredentialSource`, the interceptor, and the pool-clearing janitor from this design. No plan amendment is needed.

## Decisions and follow-ups

- ADR: [ADR-0008](../../adr/0008-secrets-broker-vault-over-openbao.md) was reviewed and does not change. The decision rests on Vault's behavior, which this spike did not test, so its status and evidence stay as they are.
- Plan changes: none. Finding 3 is a wording refinement for WP1.8 and plan section 8.8, and is not applied here.
- For WP1.8: build the `REQ-DATA-005` test on this pattern, add a periodic re-read fallback to the file source, and document the rotate, switch, clear, revoke order.
- New risks or Issues: none.
