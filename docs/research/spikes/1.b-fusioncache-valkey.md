# Spike 1.b: FusionCache backplane on Valkey 8.1 and 9.1

## Question

Do FusionCache 2.9.0 with the StackExchange.Redis distributed cache and backplane behave correctly against Valkey (which FusionCache does not certify), including cross-host invalidation, tags, an ACL-restricted user, and a Valkey outage?

## Risk reduced

- Risk [R11](../../project/risk-register.md), cross-replica cache staleness.
- [ADR-0016](../../adr/0016-cache-implementation-fusioncache.md), which treats Valkey compatibility as an inference that WP1.0 must prove.

## Time box and method

- **Time box:** one day or less. The spike took well under that.
- **Environment:** Windows x86-64 with Docker Desktop, .NET SDK 10.0.401.
- **Servers (checked 2026-10-06):** `valkey/valkey:8.1` (server 8.1.10, digest `sha256:640c5e62cea04b6d6f2084232651d0cc70362d31f4f805e7be94dbed6855e8f2`) and `valkey/valkey:9.1` (server 9.1.2, digest `sha256:418652cfb58ef879d4978c33553735d7147016032d5aefaa14c828e611eb9dfd`), both amd64. There is no `Testcontainers.Valkey` package, so the spike uses `RedisBuilder` from `Testcontainers.Redis` 4.15.0 with the Valkey image, as the Testcontainers documentation describes.
- **Packages:** `ZiggyCreatures.FusionCache` 2.9.0, `ZiggyCreatures.FusionCache.Backplane.StackExchangeRedis` 2.9.0, `ZiggyCreatures.FusionCache.Serialization.SystemTextJson` 2.9.0, `Microsoft.Extensions.Caching.StackExchangeRedis` 10.0.12, and `StackExchange.Redis` 2.10.1 (resolved by restore).
- **Method:** two independent `FusionCache` instances ("hosts" A and B) in one process, each with its own in-memory L1, an `IDistributedCache` L2, and a backplane, all against one Valkey container. Each test starts its own container on a fixed free port, so a stopped container can restart on the same address. The same 7 tests ran against both versions.

The pass criteria were fixed before the run:

| Criterion | 8.1.10 | 9.1.2 |
| --- | --- | --- |
| A value set on A is readable on B through L2 | Pass | Pass |
| An overwrite or remove on A invalidates B's L1 within a measured bound | Pass | Pass |
| Tag removal and clear propagate | Pass | Pass |
| With Valkey stopped, both hosts keep serving without throwing, and recover after restart | Pass | Pass |
| The minimum ACL command set is recorded and a narrowed ACL works | Pass | Pass |

## Results

The full suite (14 tests) passed in two consecutive runs of about 27 seconds each, and the reaper removed every container shortly after each process exited.

| Measurement | Valkey 8.1.10 | Valkey 9.1.2 |
| --- | --- | --- |
| Overwrite on A until B sees it (20 samples): median, p95, max | 14, 15, 15 ms | 14, 15, 15 ms |
| `RemoveAsync` on A until B misses | 3 to 5 ms | 3 to 5 ms |
| `RemoveByTagAsync` on A until B misses both tagged keys, with the untagged key kept | 7 to 12 ms | 5 to 17 ms |
| `ClearAsync` on A until B misses | 2 to 5 ms | 2 ms |
| Control: B with the same L2 but no backplane, after A overwrote the key | Still the old value after 2 s (L1 duration 60 s) | Same |

The polling interval was 5 ms and the Windows timer is coarse, so the invalidation numbers cluster at 14 to 15 ms. Read them as "under about 15 ms", not as a precise latency. The control row shows the backplane is what makes invalidation work: without it B stays stale until its L1 entry expires.

### Valkey outage

The test warmed both hosts, stopped the container, exercised both hosts, restarted the container on the same port, and watched convergence. Settings: L2 soft timeout 500 ms and hard timeout 2 s, StackExchange.Redis timeouts of 1 s with `AbortOnConnectFail` off, and circuit breakers of 5 s for both L2 and the backplane.

- **No exception was thrown** on any read, cold load, or write during the outage, on either version.
- **Reads, cold loads, and writes took 0 to 1 ms** once the circuit breakers were open. Cold loads ran the factory, and writes landed in L1 only.
- **Without circuit breakers it was slow.** The first version of the test left the breaker durations at their default of zero, which FusionCache documents as "never activated" (package XML documentation, 2.9.0, checked 2026-10-06). Every operation then paid the timeouts: about 3 seconds for two cached reads, 2 to 3 seconds for a cold load, and 1 second for a write.
- **B stayed on the old value.** During the outage A wrote a new value and B kept serving the old one from L1, which is the bounded staleness plan section 8.5 describes: it ends when the L1 entry expires or Valkey returns.
- **Recovery needed no new write.** About 5.3 seconds after the container restarted, B saw the value A had written during the outage, through FusionCache's auto-recovery. A write made after the restart reached B in 12 to 21 ms.
- **Open observation.** The first FusionCache call on host A right after the stop took 1.0 to 2.0 seconds even for an L1-only read that hit, while the same call on host B took 0 to 4 ms and every later call on A took 0 ms. A bare `Task.Delay(1)` probe took 0 to 15 ms, so the thread pool was not starved. The cause was not isolated. Host A had performed the writes and host B only reads. WP1.9's degradation test should assert a latency bound on the first request after an outage starts and look into this.

### ACL user

A discovery loop created an ACL user with `-@all`, ran the scenario, read `ACL LOG` for denied commands, added them, and repeated until nothing was denied. It converged in 5 or 6 iterations on both versions. The scenario covers set, read through L2, overwrite, invalidation, and tag removal.

- **Commands needed:** `client|id`, `client|setinfo`, `client|setname`, `cluster|nodes`, `config|get`, `echo`, `expire`, `get`, `hmget`, `hmset`, `info`, `ping`, `publish`, `select`, `subscribe`, `unlink`, and `unsubscribe`. `ping` appeared in only some runs because it is a heartbeat, so include it. The `client`, `cluster`, `config`, `echo`, `info`, `ping`, and `select` entries come from the StackExchange.Redis connection handshake, not from FusionCache. No Lua script commands were needed.
- **Keys:** L2 keys are `v2:` followed by the cache key prefix and the key, for example `v2:spike:probe`, and tag data is stored as `v2:spike:__fc:t:<tag>`. The `v2:` part is FusionCache's wire-format marker (`DistributedCacheKeyModifierMode`, package XML documentation, 2.9.0).
- **Channels:** the backplane channel is `spike.Backplane:v2`, built from the cache name or `BackplaneChannelPrefix` (documented as defaulting to the cache name). StackExchange.Redis also subscribes to `__Booksleeve_MasterChanged`.
- **Probe key:** StackExchange.Redis reads the key `__Booksleeve_TieBreak` when it connects. With the user limited to `~v2:spike:*` this read was denied, and the scenario still passed, so the denial is tolerated. A read-only selector (`%R~__Booksleeve_TieBreak`) removes the noise.
- **Narrowed ACL:** keys `~v2:spike:*`, the read-only probe key, the two channels above, and the command list passed the scenario with zero denied entries on both versions.

### Findings to apply in later work

1. **Plan section 8.5 needs a correction.** It says the ACL lets each environment user access `~catalog:{env}:*` and `&catalog:{env}:*`. The observed L2 keys start with `v2:`, the backplane channel is `<prefix>.Backplane:v2`, and StackExchange.Redis uses its own probe key and channel. The key rule must match `v2:catalog:{env}:*` (or change `DistributedCacheKeyModifierMode`), the channel prefix must be chosen to match the channel rule, and the command list above replaces any guess. This report does not edit the plan. It is proposed to the maintainer for approval.
2. **Set the circuit breaker durations.** The defaults leave them off. Without them, an outage makes every cache call pay the L2 and backplane timeouts.
3. **Tags work on Valkey.** `RemoveByTagAsync` and `ClearAsync` propagate in milliseconds, so the plan's `product:{id}`, `products:list`, and `category:{id}` tag scheme is workable.
4. **`config|get` and `cluster|nodes` are broader than the app needs.** They come from the client handshake. StackExchange.Redis supports disabling commands through its `CommandMap`, which would remove them from the ACL. The spike did not test that, so WP1.4 and WP1.9 should try it.
5. **Valkey 9.1.2 and 8.1.10 behaved the same** in every test. The plan's choice of 8.1 as the long-term-support line stands, and 9.1 stays a drop-in candidate.

## Conclusion

**Answer:** yes, with conditions.

FusionCache 2.9.0 with the StackExchange.Redis backplane works against Valkey 8.1.10 and 9.1.2. Invalidation, removal, tag removal, and clear propagate in about 15 ms or less. During a Valkey outage both hosts keep serving without errors and converge after restart, provided the circuit breakers are configured. The Valkey compatibility assumption in ADR-0016 is proven for functional behavior. The conditions are the three details above: the ACL patterns in plan section 8.5, the circuit breaker settings, and the unexplained first-call delay after an outage begins. None blocks WP1.9, so no plan amendment is required to proceed. The §8.5 ACL wording is a proposed clarification.

## Decisions and follow-ups

- ADR: [ADR-0016](../../adr/0016-cache-implementation-fusioncache.md) gains a dated evidence note. Its status stays proposed, and WP1.9 still accepts it.
- Plan changes: one proposed clarification to the ACL line in plan section 8.5 (finding 1), pending the maintainer's approval.
- For WP1.9: set circuit breakers, assert a bound on the first call after an outage starts, build the key and tag scheme on the tag support shown here, and use the narrowed ACL as the starting point.
- For WP1.4: the Compose Valkey user starts from the command list above.
- New risks or Issues: none.
