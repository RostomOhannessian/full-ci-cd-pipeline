# Spike 1.a: PactNet 5.0.1 on .NET 10 with a Kestrel-hosted provider

## Question

Can PactNet 5.0.1 write a consumer pact and verify a provider hosted by `WebApplicationFactory<T>.UseKestrel()` over a real TCP socket on net10.0, with provider states handled by test-only code that is absent from the production composition?

## Risk reduced

- Risk [R10](../../project/risk-register.md), PactNet dormancy or incompatibility.
- [ADR-0017](../../adr/0017-contract-first-api-design.md) and [ADR-0018](../../adr/0018-test-stack-and-quality-gates.md), which both depend on PactNet working here.
- Requirement `REQ-CON-005`, Pact verifies the primary consumer scenarios against a real socket (delivered by WP1.0 and WP4.2).

## Time box and method

- **Time box:** one day or less. The spike took well under that.
- **Environment:** Windows x86-64, .NET SDK 10.0.401, PowerShell 7.6.6. No container was needed.
- **Packages:** `PactNet` 5.0.1, `xunit.v3` 4.0.1, and `Microsoft.AspNetCore.Mvc.Testing` 10.0.12 (all checked 2026-10-06).
- **Method:** a minimal-API provider with `GET /v1/products/{id}` (an `ETag` header on success and a Problem Details body on 404), and an xUnit v3 project that:
  1. writes two consumer pacts with PactNet's V4 API (matchers for type, regex, decimal, and integer values),
  2. hosts the provider with `WebApplicationFactory<Program>` and `UseKestrel(0)`,
  3. handles provider states with a test-only `IStartupFilter` that maps `POST /provider-states`,
  4. runs `PactVerifier` against the Kestrel address.

The pass criteria were fixed before the run:

| Criterion | Result |
| --- | --- |
| A consumer pact file is written | Pass |
| Provider verification passes over a real socket | Pass |
| A deliberately broken contract makes verification fail, for the right reason | Pass |
| The provider-state endpoint is absent from the production composition | Pass |
| The native library loads on Windows x64 | Pass |

## Results

Four tests ran in about 0.7 seconds after the build, and all passed.

- **Consumer side.** Two pacts were written: `catalog-client` (an existing product with an `ETag`, and a missing product with `application/problem+json`) and `strict-client` (a field the provider does not return). The pact files record Pact specification 4.0 with the Pact Rust FFI 0.4.27 and models 1.2.8.
- **Provider side.** Verification of `catalog-client` passed. The verifier called back into the provider at a dynamic loopback port, set up each provider state through `POST /provider-states`, and matched the status, headers, and body.
- **Negative case.** Verifying `strict-client` threw `PactVerificationFailedException`, and the verifier output named the missing `discountCode` field.
- **Production composition.** A factory built without the startup filter answered `POST /provider-states` with 404, and the provider assembly contains no type with `ProviderState` in its name. The provider-state code lives only in the test assembly.
- **Native library.** The package ships `pact_ffi` for `win-x64`, `linux-x64`, `linux-arm64`, `osx-x64`, and `osx-arm64`. There is no `win-arm64` and no musl build (checked 2026-10-06, package contents). Only `win-x64` was exercised here.
- **Package facts.** PactNet 5.0.1 is MIT licensed (package metadata) and is still the newest stable release on NuGet (checked 2026-10-06).

### Findings to apply in later work

1. **`WebApplicationFactory.ServerAddress` does not exist in 10.0.12.** After `StartServer()`, read the bound address from `IServer` through `IServerAddressesFeature`, as in the snippet below.
2. **`UseKestrel()` with no argument binds the fixed port 5000.** The first run logged `Now listening on: http://localhost:5000`, which collides when test classes or other tools run in parallel. Use `UseKestrel(0)` for a dynamic port. The run then listened on ports such as 51392.
3. **The verification failure reason is not in the exception message.** It is in the verifier output. Add an `IOutput` to `PactVerifierConfig.Outputters` and assert on it, as the snippet shows.
4. **`PactVerifier.Verify()` is synchronous** and blocks its thread while the native verifier calls back into Kestrel. That is fine with Kestrel on its own threads, but do not run it on a single-threaded synchronization context.

A smaller point: the xUnit analyzer (`xUnit1051`) asks for `TestContext.Current.CancellationToken` on calls that accept a token. WP1.1 turns analyzer warnings into errors, so use it from the start.

### Key snippets

These are the parts of the spike that matter, copied from the run. The spike branch is local and is never merged, so this is the only copy.

```csharp
public sealed class KestrelProviderFactory : WebApplicationFactory<Program>
{
    public KestrelProviderFactory() => UseKestrel(0);

    public Uri BaseUri
    {
        get
        {
            var address = Services.GetRequiredService<IServer>()
                .Features.Get<IServerAddressesFeature>()!.Addresses.First();
            return new UriBuilder(address) { Host = "127.0.0.1" }.Uri;
        }
    }
}

new PactVerifier("catalog-api", new PactVerifierConfig { Outputters = [captured] })
    .WithHttpEndpoint(baseUri)
    .WithFileSource(new FileInfo(pactFile))
    .WithProviderStateUrl(new Uri(baseUri, "/provider-states"))
    .Verify();
```

## Conclusion

**Answer:** yes.

PactNet 5.0.1 works on .NET 10 against a Kestrel-hosted provider, fails for the right reason when the contract is broken, and keeps provider-state code out of the production composition. The harness that Phase 4 needs is validated, so the Pact Rust CLI fallback in risk R10 is not needed for now.

The dormancy risk itself is unchanged. PactNet has no newer release, has no `win-arm64` or musl native library, and was exercised on Windows x64 only. Linux and macOS loading is untested here, and the first Linux run of a Pact suite is in WP4.2, because WP1.1's CI has no Pact tests.
