# Spike 1.d: Testcontainers SQL Server 2022 on supported hosts

## Question

Does Testcontainers 4.15.0 start SQL Server 2022 reliably from a digest-pinned image with one shared assembly fixture, and does an EF Core 10 `rowversion` round trip work against it with Microsoft.Data.SqlClient 7.1.1? What does it cost in time and memory, and what is known about the other hosts in the support matrix?

## Risk reduced

- Risk [R3](../../project/risk-register.md), Apple Silicon and Arm contributors blocked by x86-only SQL Server.
- [ADR-0019](../../adr/0019-resource-profiles-and-host-support.md) (resource profiles and host support) and [ADR-0018](../../adr/0018-test-stack-and-quality-gates.md) (test stack).
- Requirement `REQ-DATA-005`, which spike 1.e builds on this fixture.

## Time box and method

- **Time box:** one day or less. The spike took well under that.
- **Environment:** Windows x86-64 with Docker Desktop (server 29.8.1, WSL2 kernel, Linux engine, amd64, 24 CPUs and about 30 GB allocated), .NET SDK 10.0.401.
- **Packages (checked 2026-10-06):** `Testcontainers.MsSql` 4.15.0, `Microsoft.Data.SqlClient` 7.1.1, `Microsoft.EntityFrameworkCore.SqlServer` 10.0.12, `xunit.v3` 4.0.1.
- **Image:** `mcr.microsoft.com/mssql/server` at digest `sha256:4402d880dd4c34bfa7d8705e56a86cd6c88da80a1f6bbbe741f999e76264a090` (the `2022-latest` tag on 2026-10-06; amd64; about 2.3 GB). The server reported version 16.0.4295.3, RTM, Developer Edition.
- **Method:** an xUnit v3 assembly fixture (`[assembly: AssemblyFixture(...)]`) starts one container with `new MsSqlBuilder(<image>)` and a random password. Three tests in two classes share it. Each test creates its own database. One test round-trips a `rowversion` column through EF Core 10 and checks that a stale write throws `DbUpdateConcurrencyException`.

The pass criteria were fixed before the run:

| Criterion | Result |
| --- | --- |
| The container starts repeatably | Pass: six runs, all green |
| One container is shared by every test class in the assembly | Pass: the fixture counted one instance |
| Cleanup leaves no containers behind | Pass: the reaper removed everything within about 10 seconds of exit |
| EF Core 10 and SqlClient 7.1.1 work together, including `rowversion` | Pass |

## Results

- **Startup.** The container was ready in 8.6 seconds on the first run and in 5.5 to 6.6 seconds on the other five. A whole run, including the build output and three tests, took about 8.9 seconds after the first run (15.8 seconds on the first).
- **Sharing.** The assembly fixture created one container for both test classes. Database-per-test isolation (`CREATE DATABASE`) worked on the shared container.
- **Cleanup.** After the test process exited, the Testcontainers reaper (Ryuk, `testcontainers/ryuk:0.14.0`) was still present briefly and then removed itself and the SQL Server container. Everything was gone about 10.4 seconds after exit. No container was left over after any run.
- **EF Core and SqlClient.** The project built without warnings with SqlClient 7.1.1 under EF Core 10.0.12. The loaded SqlClient assembly reports version 7.0.0.0, because the assembly version does not move with the package version. A `rowversion` property is 8 bytes, changes on update, and a stale second context throws `DbUpdateConcurrencyException`. This is the behavior that `ETag` and `If-Match` rely on in the plan.
- **Memory.** `sys.dm_os_process_memory` reported about 4.1 to 4.2 GB in use, which does not match the container. The container's own cgroup (`memory.current`) read about 1,033 MB with no cap and about 710 to 715 MB with `MSSQL_MEMORY_LIMIT_MB` set to 2048 or 1024. These are single samples taken a few seconds after startup, so they are indicative only, and they include page cache. The variable did not change `max server memory` in `sys.configurations`.

### Findings to apply in later work

1. **Pin the image by digest in code and in Compose, and set your own password.** The `MsSqlBuilder(string image)` constructor accepts a digest reference. The parameterless constructor is marked obsolete in the Testcontainers source, and the builder's default password is a well-known constant, so always call `WithPassword` with a generated value ([source](https://raw.githubusercontent.com/testcontainers/testcontainers-dotnet/develop/src/Testcontainers.MsSql/MsSqlBuilder.cs), checked 2026-10-06). A digest also meets the repository's pinning rule.
2. **Measure memory from the cgroup, not from SQL Server.** Read `memory.current` (or `docker stats`) when WP1.4 checks the `api` profile budget. The SQL Server DMV is misleading inside a container.
3. **Consider `MSSQL_MEMORY_LIMIT_MB`.** It lowered the idle footprint by roughly a third here. WP1.4 can decide on a value for the Compose profile.
4. **The reaper is privileged by default.** Testcontainers runs Ryuk with the Docker socket and in privileged mode unless `ryuk.container.privileged` is false, and its default image is already pinned by digest ([Testcontainers custom configuration](https://dotnet.testcontainers.org/custom_configuration/), checked 2026-10-06). That is a trust boundary for the threat model: CI runners and developer machines give a test dependency control of the Docker daemon.
5. **`MsSqlBuilder` sets `ACCEPT_EULA=Y` for you.** It accepts the SQL Server end-user license on the user's behalf, and the server reported the Developer edition. Record that in the tool inventory notes and read Microsoft's license terms before using the image beyond development and test.

### Host support

| Host | Result | Basis |
| --- | --- | --- |
| Windows x86-64, Docker Desktop (WSL2 backend) | Verified hands-on | This spike |
| Linux x86-64, Docker Engine | Not verified hands-on | Deferred to the first Linux CI run in WP1.1 |
| macOS Intel, Docker Desktop | Not verified hands-on | No Intel Mac available in this spike |
| macOS Apple Silicon | Not tested | Microsoft documentation, below |
| Windows on Arm | Not tested | Microsoft documentation, below |
| GitHub Codespaces | Not verified hands-on | Linux x86-64 in principle; the first Linux CI run in WP1.1 covers the same stack |

For Apple Silicon and Windows on Arm, Microsoft's container documentation says that SQL Server container images are supported only on Linux hosts running on Intel and AMD x86-64 CPUs, and that emulation or translation environments such as Rosetta 2, Prism, and QEMU are not tested or supported ([Deploy and connect to SQL Server Linux containers](https://learn.microsoft.com/en-us/sql/linux/containers/deploy?view=sql-server-ver17), page updated 2026-09-30, checked 2026-10-06). This matches the best-effort entries in [ADR-0019](../../adr/0019-resource-profiles-and-host-support.md) and plan section 4.3. Nothing in this spike tests those hosts.

The Issue for WP1.0 asks for each supported host. This spike covers one of them hands-on by the maintainer's decision. WP1.1's first Linux CI run is the planned evidence for Linux and Codespaces. The macOS and Arm rows stay open and remain best-effort until a contributor reports a result.

## Conclusion

**Answer:** yes on the primary host, with the host matrix only partly verified.

Testcontainers 4.15.0 with a digest-pinned SQL Server 2022 image, an xUnit v3 assembly fixture, SqlClient 7.1.1, and EF Core 10 works repeatably on Windows x86-64 with Docker Desktop. Startup is about 6 seconds, one container serves the whole test assembly, and cleanup is automatic. WP1.8 can build its Testcontainers suites on this pattern. No plan amendment is needed.

## Decisions and follow-ups

- ADR: [ADR-0019](../../adr/0019-resource-profiles-and-host-support.md) and [ADR-0018](../../adr/0018-test-stack-and-quality-gates.md) each gain a dated evidence note. Their status does not change.
- Plan changes: none.
- For WP1.1: run this pattern on Linux CI and record the result as the Linux evidence.
- For WP1.4: set the Compose memory behavior from cgroup measurements.
- For the threat model: add the privileged reaper and Docker socket access when a work package first uses Testcontainers in CI.
- New risks or Issues: none.
