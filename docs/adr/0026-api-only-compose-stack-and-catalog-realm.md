# ADR-0026: Run the API's dependencies in Compose, and keep one catalog realm file as the identity source

## Context and problem statement

The `api` resource profile of [ADR-0019](0019-resource-profiles-and-host-support.md) is "Compose: SQL Server, Valkey, Keycloak, and otel-lgtm, with the API on the host or in a container". WP1.4 builds it, and it owes the
first version of the realm files (`REQ-IDN-001`, `REQ-IDN-005`), host ports that need no privileges (`REQ-DX-005`), and a stack that onboarding checks can run (`REQ-CI-005`). Plan sections 8.5, 8.7, and 8.8
describe what each service must do, and the spikes of WP1.0 measured parts of it.

Facts that shape the design (checked 2026-10-10 unless a date says otherwise):

- Spike 1.b (2026-10-06) measured the Valkey command set that StackExchange.Redis and FusionCache need, and showed that FusionCache writes L2 keys as `v2:<prefix>:<key>` and its backplane channel as `<prefix>.Backplane:v2`.
  Plan section 8.5 says `~catalog:{env}:*` and `&catalog:{env}:*`. The maintainer has not decided whether to correct the plan, so the stack must work with either form.
- Spike 1.d (2026-10-06) showed that SQL Server's own memory views overstate memory inside a container, that `MSSQL_MEMORY_LIMIT_MB` lowered the idle footprint by about a third, and that SQL Server runs only on x86-64.
- Docker Compose 2.23 and newer accept inline `configs` with `content`, which Compose interpolates from `.env`. A service with `read_only: true` cannot receive one (Compose 5.5.1 refuses).
- Keycloak 26.8.0 imports a realm file at start with `--import-realm`, and fills `${NAME}` placeholders in it from the container's environment. `--hostname=<url>` fixes the issuer.
- gitleaks reads every file in the folder it scans and does not read `.gitignore`, so its working-tree scan reports the ignored `.env` that holds the generated passwords.
- **Keycloak 26.8.0 does not withhold a requested client scope from a user who lacks the role that the scope maps to.** On the running stack, a user with only `catalog-reader` that asked for
  `catalog.read catalog.write catalog.admin` received all three in the `scope` claim, with the role scope mappings in place. The `realm_access.roles` claim held only `catalog-reader`.

## Decision drivers

- Every service the API needs runs locally with one command and disposable data.
- Nothing is reachable from the network, and no port needs administrator rights.
- No credential is in the repository, and a new machine gets new credentials.
- Images are pinned by digest, and Dependabot proposes updates.
- The realm file is the only description of the realm, for Compose now, and for Testcontainers and `keycloak-config-cli` later.
- A permission is never granted because a client asked for it.

## Considered options

1. Compose with the four services, `.env` generated by `dev bootstrap`, and Keycloak importing the one realm file (chosen).
2. The same stack, with Keycloak's data on the shared SQL Server, as the cluster will have it.
3. An in-process fake issuer for local runs.
4. Aspire as the local orchestrator (held in [ADR-0019](0019-resource-profiles-and-host-support.md)).
5. For the scope finding: (a) keep the scopes and add a role claim that the API checks too (chosen), (b) stop and amend the plan first, or (c) give the human client no write or admin scope.

## Decision outcome

Chosen option: **Compose with the four services and one realm file**, because it is the smallest stack that behaves like the real one, it needs no host privileges, and the realm file can be tested against a real Keycloak.

### The stack (`compose.yaml`)

- **Images.** SQL Server 2022 `2022-latest` at digest `sha256:4402d880…`, Valkey `8.1` at `sha256:640c5e62…`, Keycloak `26.8.0` at `sha256:27b3230f…`, and `grafana/otel-lgtm` `0.35.0` at `sha256:2de1094c…`. Each carries a tag beside its digest, so
  Dependabot can propose an update, and a Pester test fails on an image without both.
- **Ports.** Everything binds `127.0.0.1` on a high port: SQL Server 1433, Valkey 6379, Keycloak 8180, Grafana 3000, and OTLP 4317 and 4318. Ports 8080 and 8081 stay free for the API and its management port. A test fails on a mapping that is not loopback or is below 1024.
- **Secrets.** `.env.example` lists names and safe defaults, and `dev bootstrap` writes `.env` with a random value for every empty name (letters and digits, 32 characters, which meet the SQL Server policy). The file is ignored, written with LF
  and no byte order mark, and restricted to its owner on Linux and macOS. A secret is never copied between machines.
- **Limits.** Every service has `no-new-privileges` and a memory limit (SQL Server 3 GB, Keycloak 1.5 GB, Grafana 1 GB, Valkey 256 MB), and none is privileged or mounts the Docker socket.
- **Health.** Every service has a health check, so `docker compose up --wait` returns when the stack works.
- **SQL Server.** The Developer edition, with `ACCEPT_EULA=Y`, which accepts Microsoft's terms for development and test use. `dev compose up` says so before it starts the container. `MSSQL_MEMORY_LIMIT_MB` is 2048.
- **Valkey.** The default user is off. `admin` runs health checks. The application user, `catalog-dev`, starts from `-@all` and adds the 17 commands that spike 1.b measured (`ping` included), the key patterns `~v2:catalog:dev:*` and `~catalog:dev:*`, a read-only
  selector for StackExchange.Redis's probe key, and the channels `&catalog:dev.Backplane:v2` and `&catalog:dev:*`. The patterns cover both the observed and the planned forms, and WP1.9 narrows them when it fixes the key scheme. This does not
  edit plan section 8.5, and the maintainer's decision on that correction is still open. The ACL is a Compose inline config, so the passwords stay out of the repository.
- **Keycloak.** Development mode with an in-memory database (`--db=dev-mem`), so every start imports the realm from the file and the realm is always what Git says. `--hostname=http://localhost:8180` fixes the issuer (plan section 8.7: "Compose uses one fixed `localhost` issuer").
  In the cluster, Keycloak keeps its data on the shared SQL Server (plan section 8.12), and the Compose stack does not, because the seed step and the memory would buy nothing in Phase 1.
- **Telemetry.** `grafana/otel-lgtm` for local development only. It bundles AGPL-3.0 components that the repository does not link or redistribute, which ADR-0004 treats as tool-only. WP1.11 provisions its dashboards.

### The catalog realm (`identity/keycloak/realms/catalog-realm.json`)

- **Scopes and roles.** The scopes `catalog.read`, `catalog.write`, and `catalog.admin`, each with an audience mapper for `catalog-api`, and the roles `catalog-reader`, `catalog-editor` (includes the reader), and `catalog-admin` (includes the editor). Each scope maps to its role with a role scope mapping.
- **Clients.** `catalog-api` is a bearer-only resource server. `catalog-cli` is public with PKCE (S256) and the device flow. `synthetic-shopper` and `smoke-tests` are confidential and use client credentials, with read-only and full access. No client enables the password grant or the implicit flow, and every client turns full scope off.
- **Users.** `reader`, `editor`, and `admin` for labs, each with one role and a profile on the reserved `example` domain, and one service account for each confidential client with the least role that it needs.
- **Placeholders.** The five secrets and passwords are `${NAME}` placeholders, and a test fails on a literal value. The file holds no hostname and no port, so the same file can serve Testcontainers and `keycloak-config-cli` later (their placeholder syntax is WP1.10's and WP3.5's concern).
- **The `platform` realm** arrives in WP3.5.

### The finding: a scope is not a permission

A client scope's role scope mapping limits which roles appear in a token, and it does not stop Keycloak 26.8.0 from granting the scope. The Compose stack showed it (2026-10-10):

| User | Asked for | `scope` claim | `realm_access.roles` |
| --- | --- | --- | --- |
| reader | all three scopes | all three | `catalog-reader` |
| editor | all three scopes | all three | `catalog-editor`, `catalog-reader` |
| admin | `catalog.read` only | `catalog.read` | `catalog-reader` |

A client that holds a scope only as optional or as default cannot be stopped from requesting it, so the `scope` claim alone cannot be the authorization decision. The realm therefore puts the roles in the access token (`realm_access.roles`, through a mapper in the
`basic` scope), and the roles that appear are the user's own roles, limited to what the requested scopes cover. `dev compose check` proves the table above. **The API (WP1.7 and WP1.10) must require the role claim as well as the scope**, which refines plan
section 8.7's "scopes are parsed from the space-delimited `scope` claim". The plan is unchanged by this decision, and the finding is flagged for the maintainer.

### Consequences

- Good: one command starts a stack that `dev compose check` proves (healthy services, a working SQL Server login, an enforced Valkey ACL, the documented tokens, and an OTLP endpoint that accepts an export), and CI runs the same check.
- Good: nothing is reachable from the network, no credential is committed, and a rebuilt realm is always the file in Git.
- Good: the finding is caught at the realm, with a test, before the API depends on the wrong assumption.
- Bad: the idle stack uses about 2.7 GB (docker stats, 2026-10-10: SQL Server 1.14 GiB, Keycloak 0.96 GiB, Grafana 0.52 GiB, Valkey 0.014 GiB), and the first start pulls about 3 GB. Mitigation: the budget is documented, doctor checks it, and WP3.0 measures the other profiles.
- Bad: `ACCEPT_EULA=Y` accepts a license on the user's behalf. Mitigation: the stack says so before it starts, the inventory records the terms, and the project uses the image for development and test only.
- Bad: the working-tree secret scan flagged the generated `.env`. Mitigation: the maintainer approved a separate gitleaks configuration for the `secrets-worktree` service only (`tools/lint/gitleaks-worktree.toml`), which keeps the default rules and allows the one path `^/repo/\.env$`.
  The full-history `secrets` service does not read it, so a committed `.env` still fails that scan.
- Bad: Valkey cannot run with a read-only root file system, because Compose copies an inline config into the container. Mitigation: the container has no privileges to add and a memory limit.
- Neutral: Keycloak's data is lost on every restart in Compose, which is the point.

### Confirmation

- **WP1.4** delivers the stack, the realm file, `dev compose check`, and the tests: 44 Pester tests over `compose.yaml`, `.env.example`, and the realm file, and 28 over the check's logic.
- The check ran against the real stack on a Windows host with Docker Desktop and inside the Dev Container with docker-in-docker (evidence record, 2026-10-10).
- **WP1.9** narrows the Valkey ACL to the key scheme that it fixes, and tests it with FusionCache.
- **WP1.10** builds `Catalog.Identity.ContractTests`, which import this file into a Keycloak Testcontainer, and the API's policies that require the role and the scope.
- **WP3.5** adds the `platform` realm and reconciles both files in the cluster.

## Pros and cons of the options

### Compose with four services and one realm file

- Good: smallest realistic stack, and the realm is testable.
- Bad: disposable Keycloak data, and a license acceptance for SQL Server.

### Keycloak on the shared SQL Server

- Good: matches the cluster.
- Bad: a database and a login to create before Keycloak starts, more memory, and no Phase 1 requirement for it.

### An in-process fake issuer

- Good: no container.
- Bad: nothing proves the realm file, and plan section 8.7 already uses an in-process issuer for API tests only.

### Aspire

- Good: first-class .NET orchestration.
- Bad: held in ADR-0019, because Compose covers the API-only path and the platform path needs Kubernetes anyway.

### The scope finding: (a) a role claim that the API checks too

- Good: closes the gap in the realm, keeps the plan's scopes, and gives the API a claim that cannot be requested.
- Bad: the API checks two claims.

### (b) stop and amend the plan first

- Good: no ambiguity.
- Bad: blocks WP1.4 for a change that belongs to WP1.7 and WP1.10, which have not started.

### (c) give the human client no write or admin scope

- Good: humans cannot escalate.
- Bad: labs that exercise the write paths as a person could not run.

## Revisit when

- Keycloak releases a version that gates a requested scope by role, which would let the `scope` claim carry the decision.
- The maintainer decides the plan section 8.5 correction, which changes the Valkey patterns.
- WP1.9 fixes the cache key scheme.
- A Compose release lets an inline config reach a read-only service.
